# The fixtures of reading 2

Written 11 November 2026, in phase 2 of [the plan for version 2](../../../../docs/history/V2-PLAN.md): "The tracker's layer, as it is, is run over every fixture and over the ledgers its own tests build, and what it says is kept as fixtures. These are the law for the port." Each file here is one ledger, with what the reference tracker's layer said of it at two times. The fold [reading 2](../../../../docs/v2/READING.md) describes is written in phase 3, and it reproduces every one of these at every step: the pass is the core's `read` now, and the core alone is held to them. Until the switch the fixtures one folder up are the law of the core in force, and nothing here changes them.

`packages/core/test/reading-fixtures.test.ts` holds the core's `read` to every file, with no tracker and no store, and runs it over version 1's fixtures too, where one piece's state differs (READING.md section 11). `pnpm conform:2` runs the same check as a script and prints, for a fixture that fails, each place the read and the file are apart. The ledger's shape, the read of it and the form of what is expected are in `packages/core/src/ledger.ts`. A second implementation reads none of the code: this file gives the form, and `impl/python/FINDINGS-2.md` records what one written from the documents and these files alone had to take from the JSON, which `python3 impl/python/conform2.py` holds to every file here.

## The file

```json
{
  "name": "challenge-1",
  "description": "…",
  "reading": 2,
  "ledger": {
    "identity": [ <the identity log's lines> ],
    "problems": [ { "envelope": <an envelope>, "lines": [ <its log's lines> ] } ],
    "blobs": { "<sha256:…>": "<the blob's bytes, base64>" },
    "coin": [ <the coin log's lines> ],
    "founding": { "0x…": 3 },
    "reads": { "<sha256:…>": 1204 }
  },
  "readings": [ { "now": "<a time>", "expect": <what the layer says at that time> } ]
}
```

The ledger is what READING.md section 1 names. `problems` holds every envelope the tracker held, in the order it lists them, so a version and the one before it are two entries. `coin` is null where the tracker carries no coin. `founding` is the standing the tracker publishes for an address (QX-1 section 2). `reads` gives, for each read a trace names that the layer asked about, its length, or null where the tracker does not hold it (QX-19 section 2).

Each ledger is read twice: at the clock of the tracker that held it, and a thousand hours on, when every window has closed and every lease and seat has run out.

## What is expected

```json
{
  "problems": {
    "<a problem's hash>": {
      "line": "<the hash of its line's first version>",
      "complete": false, "own_complete": false, "output": null, "record_output": null,
      "dropped": 0, "unoffered": [], "stake": null,
      "gold": { "committed": 0, "pending": 0, "verified": 0, "missed": 0, "overruled": 0, "lapsed": 0 },
      "locks": [], "golds": [], "challenges": [], "panels": [], "proposals": [],
      "views": [ <what the layer says of a piece> ],
      "pieces": { "<a piece's name>": 0 }
    }
  },
  "refused": {},
  "standing": { "0x…": { "standing": 2, "locked": 0, "free": 2 } }
}
```

- `line` is the name of the problem's line (READING.md section 2): the hash of its first version, which is the problem's own hash where its `prev` is null, and the oldest version its chain reaches where the ledger holds the line part of the way.
- `pieces` gives each piece the place in `views` of what the layer says of it. Pieces that say the same thing share one view, so a problem of a thousand open pieces holds one.
- A view holds the piece's one `state` (READING.md section 9); its `kind`, `extension` and `strength`; `attested`, `stake`, `gold`, `verified`, `aside` and `inherited`; its `readings`; the id of an open `challenge`; its `set`; its `record`, for a record piece; and its `trace`, with the grade and the seams.
- A `set` is its `name`, its kind, the time it was completed, and each member's id, key, time and digest. The name is the one READING.md section 5 gives, the hash of the canonical JSON of its events' ids, sorted, and a member's `id` is its event's: the reveal's, or the run's. A set of runs holds its patch and then its two runs in receipt order, each run with the digest of the patch it ran, and its kind is `check` or `score`; the trace's `traced` is null for it, since a run is no return. A set a version carries has one name on every version that shows it. A record piece's standing readings each carry their `id` the same way.
- `readings` holds every reading of the piece in receipt order (READING.md section 3): the reveal's `id`, the `problem` it names, its `key`, `root`, `vendor` and time, how it `counts`, one of `counted`, `kept`, `aside` and `struck`, `why` where it counts for nothing, and `by`, the id of the challenge or the gold reveal that struck it. The reasons are a closed list, `WHY` in `packages/core/src/readings.ts`, and a second implementation says the same words, which are written out under The reasons below. Since a reading is named by its id, two pieces that hold a reading share no view.
- `complete` is the layer's, over the inherited squares, and `own_complete` the problem's own (QX-23 section 4). `output` is the hash of the output document and `record_output` the hash of the record document (QX-20 section 4). `dropped` is a count of the events of the types reading 2 adds that the pass took for nothing, a lock no free standing covers or a gold or a rank the rules refuse; what reading 1's fold drops, a reveal with no commit among them, is left off the record and not counted here. The reference's door refuses what the pass would drop, so every file a door alone wrote says 0. `dropped-1` holds such events written past the door, and counts five: a challenge, a lock, a gold and two ranks. A verdict the pass takes for nothing is on its challenge's list and is not counted here, and a rank is on its panel's list and counted here too. `unoffered` lists the hashes of the judge pieces whose panel is not decided, sorted, and `gold` counts the problem's commitments by what became of each.
- `proposals` holds each proposed piece that stands (QX-22 section 3). A ledger says nothing of what a tracker lists or of the names it holds, so `pursued` names every version of a fork that holds the piece, in the order of their hashes, where a tracker answers the fork's head alone, and `proposer` is null.
- `refused` names each problem the layer could not read, with the reason.
- `standing` holds every root a line of the ledger counts for, and every owner.

## The keys

Each thing listed is written with the keys below and no others, and a key that holds nothing says null, so none is left out. A time is written as a receipt writes it, a hash carries `sha256:`, and a key or a root is an address. Added 11 November 2026 for `impl/python/FINDINGS-2.md`, entries 4 to 13, which took each of these from the JSON, and `packages/core/test/fixture-keys.test.ts` holds this part to every file here.

A view:

- `state`, `kind`, `extension` and `strength`. A verifier says its kind, the extension that reads it and how strongly it earns a square: `agree`, null and `agreed`; `check` or `score`, null and `reproduced`; `human`, `QX-3` and `agreed`; `judge`, `QX-2` and `judged`; `attest`, `QX-10` and `attested`; `record`, `QX-20` and `recorded`. A verifier no rule knows says null for all three, and its piece is `unknown`.
- `attested` is true where the piece's set is an `attest` piece's. `stake` is the standing the piece asks at the time read, 0 where it asks none.
- `gold` is null, `match`, `miss` or `overruled`, and `verified` is true where it is `match`. Both are said at the version the gold names: another version of the line that keeps the piece says null and false, though it shows the set.
- `aside` holds the ids of the reveals set aside, sorted. `inherited` is null, or the `problem` where the square stands and its `state` there.
- `challenge` is the id of the last challenge on the piece at any version of its line, the last by its receipt's time and then by its id, and it is kept once the challenge is decided. It is null where the piece has had none.
- `set` is `name`, `kind`, `completedAt` and `members`, each member an `id`, a `key`, an `at` and a `digest`. The kind is the set's own and not the verifier's: a set of reveals says `agree` on a `human`, a `judge` or an `attest` piece too, and the view's `kind` says which verifier made it. A set of a `check` or a `score` piece lists the patch and then its runs, as `run-1` holds.
- `record` is null, or `wanted`, `recordedAt` and `standing`, each standing reading written as a set's member is.
- `trace` is `traces`, `traced`, `seams`, `aside` and `record`. A trace is `id`, `key`, `at`, the `reveal` it names, its `reads`, each a `url`, a `hash`, an `at` and a `media`, and its `rests`, each a `field`, the place of a `read` in the reads and a `span`. `traced` is `both`, `one`, `none` or null. A seam is a `field`, a `why`, one of `source`, `span`, `reading` and `unknown`, and two `sides`, each a `key`, a `value`, a `read`, a `span`, a `passage` and `aside`; the passage is null here, since a ledger holds no read's bytes, so no fixture holds an implementation to a passage. `aside` holds the ids of the reveals set aside, and `record` is null or a record piece's grade: `wanted`, `standing`, `grounded`, `roots`, `vendors` and `keys`.

A problem's lists, `locks`, `golds`, `challenges`, `panels` and `proposals`, and its two sums:

- `gold` counts the commitments of the problem's golds, the dropped left out: `committed` is all of them, and each is one of `pending`, `verified` where it matched, `missed`, `overruled` and `lapsed`, which a commitment is where it was still pending when the problem settled. A lapsed commitment goes on saying `pending` as its own `outcome` in the gold's list, since a lapse is read at the time asked and written on nothing.
- `stake` is null, or the rule in force at the time read: `min`, and `pieces`, the names of the pieces and the families it is on, null where it is on every piece.
- A lock is `id`, `problem`, `piece`, `name`, `key`, `root`, `at`, `kind`, `amount`, `coinId`, `forfeitedAt` and `restoredAt`. The kind is `standing` or `coin`, and `coinId` is the coin log's lock a coin lock names.
- A gold is `id`, `problem`, `key`, `root`, `at`, `stake`, `commitments` and `forfeitedAt`. A commitment is `h`, `piece`, `name`, `outcome`, `revealedAt`, `projection`, `struck` and `struckRoots`. The piece, its name and the projection are null until the reveal. The outcome is `pending`, `match`, `miss`, `overruled` or `dropped`, the last where a challenge overruled another commitment of the gold while this one was pending. `struck` holds the ids of the events of the set a miss struck, and `struckRoots` their roots.
- A challenge is `id`, `problem`, `piece`, `key`, `root`, `at`, `stake`, `ground`, `against`, `parties`, `seed`, `order`, `seats`, `outcome`, `decidedAt`, `struck` and `dropped`. `against` is `acceptance` or `gold`. `parties` holds the roots of the accepting set and then the owner, and against a gold the owner alone. `order` is the pool in the order of the draw, and is empty where the pool was under three and the challenge void for it. A seat is `root`, `offeredAt`, `lapsedAt` and `verdict`, and a verdict is `id`, `key`, `root`, `at`, `for`, which is `challenger` or `author`, and `return`. The outcome is `open`, `held`, `failed` or `void`. `struck` holds the ids of the set's events once the challenge held, each reveal's id and then its commit's, member by member, and `dropped` each verdict that did not count, its `id` and `why`, in receipt order. The verdicts are read once the judges are drawn, so a challenge void at the draw lists none. The reasons are asked in this order, and the first that holds is said: "the challenge was decided", where the outcome is no longer `open`; "names another problem or piece than its challenge"; "signature is not the key's"; "body.for: one of challenger, author"; "body.return: an object"; "the key may not sign a verdict"; "not a judge drawn for this challenge"; "this judge has answered"; "this seat lapsed"; and then what the return lacks, "a verdict on a check or score piece carries no return" or the first fault of the return against the piece's schema. `dropped-1` holds the first, the seventh and the eighth, and `unsaid-1` holds the others. A seat is offered at the challenge's receipt and no earlier, so a verdict received before it says "not a judge drawn for this challenge", whoever is drawn after, and `early-1` holds it.
- A panel is `piece`, `name`, `panel`, `majority`, `wanted`, `candidates`, `seed`, `completedAt`, `order`, `seats`, `outcome`, `winner`, `decidedAt` and `dropped`. `panel` is the number of seats, `majority` the number that decides and `wanted` the candidates the piece asks for. A candidate is `digest`, `key`, `root`, `at` and `return`, in receipt order. `order` is the pool in the order of the draw, and is empty where the pool was under the panel's seats and the panel void for it. A seat is `root`, `offeredAt`, `lapsedAt` and `rank`, and a rank is `id`, `key`, `root`, `at` and `ranking`, the candidates' digests in the order ranked. The outcome is `open`, `decided` or `void`, and `winner` is the digest a majority ranked first. `dropped` holds each rank that did not count, its `id` and `why`, in receipt order, and each is counted in the problem's `dropped` too. The ranks are read once the judges are drawn, so a panel void at the draw lists none. The reasons are asked in this order, and the first that holds is said: "the panel has decided"; "signature is not the key's"; "body.ranking: a list of candidate digests, first choice first"; "body.ranking: each digest once"; "the key may not sign a rank"; "not a judge drawn for this piece"; "this judge has ranked"; "this seat lapsed"; and "body.ranking: the 2 candidate digests, each once", with the number of the panel's candidates, where the ranking is not those digests. `dropped-1` holds the first and the sixth, and `unsaid-1` holds the others. A seat is offered at the receipt of the panel's last candidate and no earlier, so a rank received before it says "not a judge drawn for this piece", whoever is drawn after, and `early-1` holds it.
- A proposal is `id`, `under`, `name`, `hash`, `piece`, `why`, `key`, `root`, `at`, `proposer`, `worked`, `taken` and `pursued`. `under` is the version the proposal names, `hash` the hash the proposed piece has, and `piece` the piece as the event's body gives it.
- A `seed`, a challenge's or a panel's, is sixty-four hex characters with no `sha256:` before them.

The whole:

- The views are in the order their first pieces have in the envelope, its families expanded, and two pieces share a view where the two say the same in every key.
- `standing` holds the root of the signer of every line of the ledger, the identity log's, the coin log's and each problem's, and the root of each envelope's owner, each root as the identity log leaves it at its end.
- A problem is refused in the words of its first fault, asked in this order: `envelope: ` and then the first fault of the envelope's shape, `envelope: not signed by its owner`, `blob <name>: <hash> not present` for a blob the envelope names that the ledger does not hold, and `blob <name>: does not match its hash`. The fixtures hold the second and the third.

## The reasons

A reading that counts for nothing says why in one of these words, and no others (READING.md section 3). The list is closed, and `packages/core/test/reasons.test.ts` holds it to the reference's. The fixtures hold all twenty, and the list would say which they did not.

- "its root is related to the owner"
- "its root is related to the root of an earlier reading"
- "its root is related to the root of a reading in the set"
- "an earlier reading from its vendor says the same"
- "the set holds a reading from its vendor"
- "it differs from the set on an agree field"
- "the set was made before it"
- "the set was made without it"
- "the set was made on another patch"
- "it is not from a person's seat"
- "the readings the piece asks for stood before it"
- "an earlier candidate gave the same return"
- "the candidates were in before it"
- "the panel ranked another first"
- "its panel is void"
- "its piece asks a verifier this reading does not implement"
- "it rests on nothing where another reading rests on the record"
- "a challenge held against its set"
- "the owner's gold missed its set"
- "the fold without the struck events does not hold it"

## How they are written

```bash
QUILT_WRITE_READING=1 pnpm exec vitest run packages/tracker
```

The writing stays with the tracker's tests, since a ledger is what a booted tracker's store was left holding (`packages/tracker/test/reading.ts`). With the variable set, the helper every tracker test boots a tracker through keeps each one, and once a test file has run, writes the ledger each tracker was left holding as `<the test file's name>-<n>.json`. No such fixture is picked by hand. A test also keeps a tracker as it stands at a point it passes through (`keepReading`), for a state it does not end in, and a ledger it builds by hand with no tracker (`keepLedger`), each under a name the test gives. A run without the variable writes nothing.

```bash
QUILT_WRITE_READING=new pnpm exec vitest run packages/tracker
```

With `new` only a fixture not yet kept is written, and every file that stands is left as it is. This is how a fixture is added.

Four kinds of ledger are left out: one with no problem, one of more than a thousand lines, one whose file would pass 256 KB, and one the layer throws on, which a test builds to show the throw.

The tests sign with fresh nonces and their clocks are their own, so a second writing gives new ids throughout. A rewrite with `1` therefore replaces every file, ledgers and all, and it is done only where the ledgers themselves are meant to change, in a pull request that says why. Between rewrites the files stand as they are and the code is held to them.

## How they are said again

```bash
pnpm --filter @bitquilt/core exec tsx fixtures/say-again.ts
```

Where the read's answer over the ledgers kept is meant to change, the ledgers stand and the answers alone are written again: `packages/core/fixtures/say-again.ts` reads each file's ledger at each of its times with the core's `read` and writes what it says where the answer was kept. No id, time or signature changes, and a file whose answers stand is not written. It is run only in a pull request that says which answers changed and why, and that shows nothing else did.
