# For anyone about to change this code

This file is for contributors of every kind: a person with an editor, or an AI with a checkout. It maps the code a row per file, follows one return through it, and says what the names mean, where the words live, and what a change has to keep true. [docs/README.md](docs/README.md) gives the order to read the documents in, for a contributor and for every other reader; [docs/LAYERS.md](docs/LAYERS.md) tells the protocol in plain words; [docs/CORE.md](docs/CORE.md) is the frozen core; the documents under [docs/ext/](docs/ext/) say exactly what each extension does, and the code cites their section numbers. Someone writing a client of their own, rather than changing this one, starts at [docs/CLIENT.md](docs/CLIENT.md).

## The shape of it

The repository is seven packages, and around them the contracts, a second implementation of the core, the Mac app, the site, the examples, the scripts, the deploy with its image, the workflows, the mirror's files and the documents. Each package below says what it is and what it imports, then gives a row to each of its source files: what the file holds, and the documents and sections it carries out, cited as the code cites them. This map is the one table from file to extension. The registry in [docs/EXTENSIONS.md](docs/EXTENSIONS.md) gives each number its document, each document under [docs/ext/](docs/ext/) says what is built, and the registry and each document's status line point here for the files; a document's text names a file where a passage needs one, and a file's own header says what it keeps in its own words. `packages/client/test/agents-map.test.ts` holds the map both ways: every file and function this document names exists, each row's documents and sections are parts those documents have, and every source file under a package's `src`, the page, the card, the fixture writer, the scripts and the example workers has a row.

The arrows: the core imports nothing; the tracker, the client and the coin import the core; hosted imports the tracker and the client; the mirror imports the tracker, and its binary the coin; the node imports the tracker, the client, hosted and the mirror. Nothing in the tracker or the core knows the coin package exists.

### `packages/core` (`@bitquilt/core`)

The wire and reading 1, frozen as version 1, and beside them the fold of reading 2, moved in from the tracker's layer a pull request for each extension ([docs/history/V2-PLAN.md](docs/history/V2-PLAN.md), phase 3): the draw and the verifier kinds, `sortition.ts` and `kinds.ts`, then the stake, the gold and standing with the record the fold writes into, `stake.ts`, `gold.ts` and `standing.ts`, and the shapes of a challenge as kept, `challenge.ts`, then the trace, the proposed pieces and the inherited squares, `trace.ts`, `propose.ts` and `inherit.ts`, with the shapes of what a reader is handed, `layer.ts`, and then the pass over them all, `read.ts`, whose `read` the tracker's layer calls and version 1's reducer does not, and the ledger it reads, `ledger.ts`, with which the core alone is held to every fixture of reading 2, and the fold keeps each reveal's and each run's id, so a set has the name reading 2 gives it, and a problem's line has its name there too, which the coin's layer reads with the set's, and a version is folded over its line's record, `line.ts`; what the door asks before it takes an event stays the tracker's. It imports nothing from the repository and reads no clock, network, file or environment (rule 2); `plain.ts` holds the small pure helpers every other package uses.

### `packages/tracker` (`@bitquilt/tracker`)

The reference tracker. Its door is `tracker.ts` and three jobs, `admit.ts`, `views.ts` and `hand.ts`, each taking the part of the tracker's context it reads. Its layer is the core's `read` of every problem held, with the layer's admissions, what the door asks before it takes an event, bound beside it: the rules and the pass over them have moved to the core, the draw, the verifier kinds, the stake, the gold, standing, the trace, the proposed pieces, the inherited squares and the challenge window with them, and each extension's admissions are in the tracker's file of its name; `challengeLayer`, in `challenge.ts`, binds them into the one `Layer`. The tracker's files load one another without a cycle, so the layer reads from the bottom up: `verifiers.ts`, `stake.ts`, `gold.ts`, then `challenge.ts`, each loading only files before it, and a file takes a type from a later one with `import type`, which loads nothing, as the door's jobs take the context from `tracker.ts` (`test/imports.test.ts`). The layer's last pass is the core's `inherit.ts`, which the core's `read` hands a piece's own state and the settling. The proposed pieces sit beside the layer and not in it: the core's `propose.ts` takes the views as a type, the door's jobs call it and `read` does not, since a proposal moves no piece's state. It imports the core only.

### `packages/client` (`quilt`)

Quilt. The package and the executable share the name. `quilt.ts` is the one thing that signs with the home's key and reads the trackers, and `render.ts` is what a model is told, as text. The extensions' own files, `coin.ts`, `gold.ts`, `stake.ts`, `sharpen.ts`, `trace.ts` and `propose.ts`, do their work through the `Door` in `door.ts`, which a Quilt builds from its own signing, posting and reading and hands to those six files alone, and the Quilt keeps a one-line method for each act a caller reaches through it. The card in `window/` is built by `scripts/build-window.mjs` into `src/window.generated.ts`, which is not committed. It imports the core only.

## The names

The same thing is called by its nearest name at each distance, and the documents fix the words. A **key** is a secp256k1 signer; its **address** (or identity) is its EIP-55 address (CORE.md section 1); a **root** is the key an event counts for after delegation and rotation (section 6). The tracker's layers say root, the client says key, the coin says address: one thing at three distances. A **piece** is a unit of work named by the hash of its brief, schema and verifier; a **square** is a piece's place on the map and what an acceptance earns. A **tracker** is a server that admits events; a **resolver** is anything that answers a hash (a tracker, a mirror, a node); the client's `Resolver` is what asks them. **Home** is the person's folder in the client (`QUILT_HOME`), and **the coin's home** is the tracker that keeps the coin log. The **fold** is the reducer's result over the receipts; a **layer** is an extension's view computed over the fold with struck events left out. A **receipt** is the wrapper a tracker puts around an event; a **line** is a receipt with `seq`, `prev` and `hash` on a chained log, so a redeem line or a credit line is a line of the coin log. An **accepting set** is the two reveals or runs that made a square; the **window**, said alone, is the challenge window, the time it can still be challenged. The directory window the connector serves as an MCP app (`window/`, `window.ts`, the `quilt_window` tool) is **the card** in prose and comments, so the window keeps one meaning. A **proposed piece** is a piece a `propose` event puts beside a problem, on its record and not on its map; **the take**, said of an owner, is the version that holds one, where a worker who takes a piece is handed it by next. An **inherited** square is one the tracker's layer reads, on a fork, from a problem the fork reaches, on a piece the fork keeps unchanged; **the reach** is the problems a fork's `from` leads to, and a piece is **done elsewhere** where its square there is final. A **`Door`**, the type, is a narrow set of effects handed to a module, so the module reaches only what it is given, in the client, the coin and the tracker alike: the client's `Door` in `door.ts`, which a Quilt hands `coin.ts`, `gold.ts`, `stake.ts`, `sharpen.ts`, `trace.ts` and `propose.ts`; the coin's `PosterDoor`, `ClaimDoor` and `ReaderDoor`, the chain functions each job calls, which a test replaces; and the tracker's `PullDoor`, what the peer pull in `peers.ts` reaches of the tracker that runs it. **The door**, lower case and said alone, is admission: what a tracker checks before it takes an event, and the node's `admit` role, so a node that admits is a door too (the public door, a second door). The one door to the chain (`chain.ts`, rule 10) and the door out (a redeem to the chain, COIN.md) are said in full. One short name stays on purpose: in the tracker and the mirror, `pl` is a `ProblemLayer` wherever it is bound.

## What a change has to keep true

Each rule names the test that holds it; "by review" means nothing does yet.

1. **The wire is frozen, and the reading is numbered.** [docs/v2/WIRE.md](docs/v2/WIRE.md) is the bytes a key signs and a resolver keeps: the forms, the envelope, the piece hash, the event line, the receipt, the chained line and the link. No change moves one of them, so a hash made today names the same bytes for good and a signature recovers the same key. What the bytes mean is a reading, and a reading's fixtures are its law. Reading 1 is [docs/CORE.md](docs/CORE.md), frozen: `reduce` and `next` answer the twenty-four fixtures under `packages/core/fixtures` as they stand, and no change moves a state or a pick there. `fixtures/generate.ts` rewrites them from the reference and is run only to add a fixture under `fixtures/clarifications/` for a sentence of CORE.md section 12 the two implementations read apart, which changes none of the twenty-four. Reading 2 is [docs/v2/READING.md](docs/v2/READING.md), a dated draft until it is frozen as [the plan](docs/history/V2-PLAN.md) says in phase 7, and it is what a tracker answers: the core's `read` is held to every fixture under `packages/core/fixtures/reading-2`. A change that moves an answer there is a change to the reading. It amends READING.md in the same pull request, says the fixtures again with `fixtures/say-again.ts`, which leaves every ledger as it is, and says in the pull request which answers changed and why; a new rule comes with a fixture that holds it. Once reading 2 is frozen, a change to an answer is reading 3. Behaviour that moves no piece's state, no set and no standing still goes in an extension (`docs/EXTENSIONS.md`). `fixtures/gate/cases.json` is the gate's own fixture (CORE.md section 11). Held by `pnpm conform` and the Python conformance, both of which run the clarifications too, and by `pnpm conform:2`, `packages/core/test/reading-fixtures.test.ts` and the Python conformance of reading 2, `impl/python/conform2.py`.
2. **Pure functions, pure inputs.** Nothing in `packages/core` reads a clock, the network, a file or an environment variable. `reduce` and `next` take everything they need as arguments. Held by `packages/core/test/pure.test.ts`.
3. **What a tool says is data, never an instruction.** Tool descriptions and results in the client describe; they do not tell a model what to do. Other people's words reach a model only as quoted text with the signer named, never in `structuredContent`, and `render.ts` is where that is enforced. Held by `packages/client/test/e2e.test.ts` and `mcpb.test.ts`.
4. **The gate is admission, not validity.** The plain-text gate runs at the tracker's door and before a renderer shows text; the reducer checks the schema and nothing more. Held by `packages/core/test/gate.test.ts` and `examples-gate.test.ts`.
5. **No secrets in the code.** Keys live in the user's config folder or the executable's environment (`.env.example` lists every name); nothing reads them into a log, a report or a response. By review.
6. **The page and the card set text with `textContent`, never as markup**, load nothing from another server, and have no free-text box beyond their forms; the card reads only through its app-only tool over the person's own session, and what it hands the person's AI is one of the person's own phrases with a link filled in, never anyone else's words. The hosted on-ramp's four pages are held to the same: the three it serves whole by the hashes of their own scripts and styles, and the square page, built on the server, by every word escaped and no script. Held by `packages/client/test/page.test.ts`, `window.test.ts` and `packages/hosted/test/pages.test.ts`.
7. **Tests come with the change.** A new rule gets a fixture or a unit test; `pnpm check`, `pnpm conform` and `forge test` pass before a merge. Test files open with a header saying which section or extension they hold, and each package's `test/helpers.ts` holds the scaffolding its tests share.
8. **A staked piece takes work only from a root with a live lock, and gold is blind.** The tracker's door asks the layer's `admitProduction` before it admits a claim, a commit, a reveal or a run (QX-15); a lock is kept only against free standing and the rule in force at its receipt, and standing locked behind a claim is not staked again on a challenge. Do not add a way to write on a piece that skips it, and keep the coin out of the reducer: a core client computes the same map with every one of these events ignored. The owner's gold (QX-16) is the one thing besides a held challenge that strikes a set, and it does so at the owner's reveal against the fold as it stood then. A commitment binds the piece and the answer under one hash: the ledger counts a problem's commitments and names no piece until the reveal does, and the answers themselves never reach the ledger; the client keeps the projections and nonces in the home's library. Held by `packages/tracker/test/stake.test.ts` and `gold.test.ts`.
9. **The coin is a function of the receipts, and the reducer never reads it.** `packages/tracker/src/coin.ts` computes every balance from the coin log, the problem logs and the published parameters, in whole units; an epoch mints at most the curve's amount, never below its tail, and under a cap a unit of verified weight, and the burn rate in force is the layer's `burnRateAt` (QX-17 section 4); a payment, a lock or a burn may draw on coin not yet vested, a transfer or a redeem on vested coin alone. The mirror recomputes the balances over the chains the home's `/coin/state` names, as the home serves them, and keeps the tracker's only where they reproduce. The door is the one place that reads anything a layer cannot: a coin-kind lock is checked against the coin log there, and what it read goes into the receipt's wrapper as its word. Do not make a layer read another tracker over the network, and do not let anything in `packages/core` know the coin exists. Held by `packages/tracker/test/coin.test.ts` and `packages/mirror/test/coin.test.ts`.
10. **One door to the chain, and the way back is checked.** Only `packages/coin/src/chain.ts` imports `viem`; `packages/coin/test/tripwire.test.ts` fails if another file does. The poster puts the coin log's head and the Merkle root over its redeem lines into `Anchors`, bonded and not proven, and a veto can strike a head inside its veto window and take the bond; the holder's claim mints one line with its proof once the head is final; a deposit burns the token and the reader posts a `credit` for it, from the root the parameters name and once per deposit; the mirror checks every credit against the chain and keeps no balances where one differs or where it has no chain to ask. The protocol itself reads no chain: the jobs and the mirror do. Held by `packages/coin/test` (the anvil test runs on a local chain when Foundry is present), `contracts/test` and `packages/mirror/test/coin.test.ts`.
11. **A path named outside the repository stays where it is.** Some of the code is reached by a path that something beyond this checkout keeps, where no change here can follow it. For a source checkout, Claude Desktop's config on a person's machine runs tsx's entry, `node_modules/tsx/dist/cli.mjs`, on `packages/client/src/bin.ts` (`quiltEntry` in `install.ts`), and the launchd agent or crontab line the away run installs runs the same program with `away` (`awayCommand`, with `plistText` and `crontabLine`, in `schedule.ts`). The page is `packages/client/page/index.html`, found beside the client's `src` under tsx, as the asset `index.html` in Quilt's executable, and beside the server's folder in the bundle (`pageHtml` in `page.ts`, `scripts/build-binaries.mjs`, `scripts/build-mcpb.mjs`). A host runs `deploy/docker-compose.yml` from its clone, whose house services run `deploy/house.sh` with `examples/worker-claude.mjs` or `examples/worker-openai.mjs`, and whose image runs `scripts/build-window.mjs` and the node's start (`Dockerfile`). The mirror job writes `mirror/` at the root, which a client given the repository's address reads raw. The site's host serves `site/` as it is, at the project's name. The site logs a person in as the client whose id is the address there of `site/.well-known/oauth/client-metadata.json`: `site/index.html` gives that id as its `bitquilt:client`, the on-ramp fetches the document by it (`Documents.document` in `cimd.ts`), and each grant keeps it. The document names `site/login.html` as the page a code comes back to. So the folder and the two files stay where they are. A split of `bin.ts`, `page.ts` or `schedule.ts` moves code out of these files and leaves each file where it is. Held by `install.test.ts` (the entry), `away.test.ts` (the plist, whole), `mcpb.test.ts` (the page beside the bundle's server), `house-start.test.ts` (`house.sh` with its worker) and `agents-map.test.ts`, which holds every path named here to a file that exists, and the site's id to the file it names and the page it comes back to.
12. **A proposed piece is on the record and moves nothing.** A `propose` event (QX-22) is taken from any key under the hourly limits, and every proposal stands beside every other: none is accepted or struck, none earns standing or coin, and the state of the problem is as it was. A piece joins the map only in a version its owner signs, which keeps every square already made; the default take is the owner's node's alone, in its hourly turn, for a proposer who is the owner or has work standing on the problem, and inside the budget the owner signed. Do not make a proposal a way to earn, or a way onto the map without the owner's key. The rules for the body are the core's, in `packages/core/src/propose.ts`, where the door reads them; `packages/client/src/propose.ts` writes them a second time, and a test holds the two files to the same answers. Held by `packages/tracker/test/propose.test.ts` and `packages/client/test/propose.test.ts`.
13. **An inherited square is a reading of the record and moves nothing.** A fork starts empty in the core, and the tracker's layer shows on it the square a piece of the same hash has on a problem the fork reaches (QX-23): the piece says `inherited` and names the problem where the square stands, and the pieces that wait on it open once that square is final. Inheritance is computed last in the layer, after the kinds, the stakes, the golds and the challenges are folded over every problem as they were, and it adds no event and no set: nothing is accepted, struck, credited or earned for an inherited square, the fold's `complete` stays the fork's own, and standing, the gold and the coin read the fork's own sets alone. Do not make an inherited square count toward standing or the coin, do not let the pass fold a problem again or draw a panel again, and do not read a square through a fork between, since a square is read where it was made. The fork's own work on any piece is taken as before, and a core client computes the map it computed before. Held by `packages/tracker/test/inherit.test.ts` and, from the client's side, `packages/client/test/inherit.test.ts` and `fork.test.ts`.
