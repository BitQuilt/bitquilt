# QX-14: discovery over relays

Status: Draft. Written and first implemented 26 October 2026 in the Quilt client (`packages/client/src/relay.ts`). [EXTENSIONS.md](../EXTENSIONS.md) says what an extension may do; [APP.md](../APP.md), Search, and [PROTOCOL.md](../PROTOCOL.md), Later, name this one; QX-13 is the announcement it carries.

**Abstract.** A tracker is one place a problem is found, and a tracker is someone's. Nostr relays are hundreds of places that store signed events for anyone, answer filtered requests, need no open port from the person, and use the curve BitQuilt's keys already use. This extension posts a problem's announcement (QX-13) to relays as a relay event, and searches relays for announcements, so a problem can be found by its name with no tracker in between. The relay event is transport; what a reader trusts is the announce inside it, signed by the owner, and the hash it names.

## 1. The relay event

A NIP-01 event of kind `30177`, parameterized replaceable, so a relay keeps one per key and problem and the latest replaces the rest:

| Field | Value |
| --- | --- |
| `pubkey` | The x-only public key of the signer's secp256k1 key, as Nostr writes it. |
| `kind` | `30177`. |
| `tags` | `["d", <problem hash>]`, `["title", <title>]`, and one `["t", <topic>]` per topic of the announce, at most eight. |
| `content` | The BitQuilt `announce` event, as its JSON, signature included. |
| `id`, `sig` | As NIP-01: the hash of the serialized event, signed with BIP-340 Schnorr by the same secret. |

A reader accepts the event when its id and Schnorr signature verify, the content is an `announce` that passes the core's shape check and signature check, and the `d` tag is the announce's problem. The key that signed the relay event need not be the owner's: a seeder may repost an owner's announce, and the reader learns the owner from the announce, never from the relay event.

## 2. What is found

A search asks each relay the person has chosen for the latest `30177` events, reads the announcements out of them, keeps the latest per problem, and filters locally by the words of the query against the title, slug, statement of done and topics. What comes back names the problem by hash, with the trackers and mirrors the announce listed as hints, so the problem is then opened as any `quilt:` link is: from a tracker in the hints, a mirror, or the cache. A relay carries no map; the counts in a relay result are the announce's, as of when it was posted.

## 3. The client

- `relays` in the client's config, or `QUILT_RELAYS`, lists the relays; the default is none, as a torrent client ships with no tracker of its own.
- `publish` posts the announce to the trackers as before and then to every relay listed; the result says which relays took it.
- `search` asks the trackers and the relays together and merges the results by problem hash; a result from a relay says so.
- Nothing from a relay reaches a model except the quoted title, the quoted statement of done and the topics, through the gate, with the publisher named, as APP.md says of every index.

## 4. What this does not do

- It does not replace trackers. A relay stores announcements, not events of the problem; the map is still computed from a ledger a tracker or a mirror holds.
- It does not curate. The curation a tracker does by admission, a relay does not; the person's own block list of keys and relays, in the app, is the only filter, as APP.md says.
- It does not do the keyword DHT among long-lived nodes that the registry row names for later.

## 5. Tests

`packages/client/test/relay.test.ts` runs a relay of its own: a publish reaches it and is found there by a client with no tracker configured, with the tracker hint carried; an event with a broken signature, a foreign kind, or a `d` tag that is not the announce's problem is dropped; the latest announce per problem wins.
