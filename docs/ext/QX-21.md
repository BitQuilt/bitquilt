# QX-21: doors fold each other's chains

Status: Draft. Written and first implemented 2 November 2026 in the reference tracker; [AGENTS.md](../../AGENTS.md#the-shape-of-it) names the files that carry it out. [EXTENSIONS.md](../EXTENSIONS.md) says what an extension may do; [PROTOCOL.md](../PROTOCOL.md), Propagation, said from the first that trackers may pull each other's events for hashes they both carry, taking the union by event id and keeping the earliest receipt; this document says exactly how the reference tracker does it. [CORE.md](../CORE.md) section 5 is the rule it rests on: receipts merge by the union of their wrappers, and the earliest decides a time.

**Abstract.** A problem is published to several trackers and worked through whichever one a client reaches, so each tracker's chain for it is a subset of what was signed. Until now the subsets met only in a mirror. With this extension a tracker names peers, pulls each peer's identity log and its chain for every problem both hold, and admits every event it lacks through its own door, as if the signer had posted it here with the peer's receipt. Nothing is trusted on the peer's word: the chain is verified, every event's signature and shape are checked, and the door's own rules decide, so two doors converge on everything both admit and differ where their layers' rules differ, which is the same as if the event had been posted to both. There is no agreement protocol and none is needed: events are signed facts, and state is a function of the set.

## 1. Peers

A tracker's peers are the trackers it names (`QUILT_PEERS`, published as `peers` in its well-known document, which clients already read). Naming a peer is the tracker's own decision, as admission is: it says whose chains this door will pull through its rules. A peer need not name the tracker back. A tracker whose well-known says `pull` carries this extension and says how often (`every_ms`).

## 2. The pull

Every five minutes, the first a minute after start, one pull at a time, for each peer in turn:

1. The peer's well-known document is read; a peer that does not answer is noted and passed over.
2. The peer's identity log (`GET /k/events`) is pulled first, since a name, a delegation or a rotation changes what later events count for.
3. Then, for every problem this tracker holds, the peer's chain for it (`GET /p/<hash>/events`), page by page; a problem the peer does not hold answers nothing and is passed over. Problems the peer holds and this tracker does not are not taken: a tracker admits what is published to it, and a pull is not a publication.
4. The reads a trace names (QX-19) that this tracker lacks are taken from the peer under their hashes (`GET /b/<hash>`) before the trace is admitted, since a trace is admitted where its reads are held; one that does not hash right is not kept, a read named by anything but a hash is not asked for, and the trace is refused as its own rule refuses it.

For each log, the chain is read whole and verified from its genesis as QX-11 says; a chain that does not verify is left whole, and the pull says so. Then each line is taken in the peer's order:

- An event already on this tracker's chain, by id, is passed over.
- An event whose shape or signature does not hold is refused with the reason and not folded, its body held first to the door's bound on nesting and to no field named `__proto__` (PROTOCOL.md, What the door answers), and an event this door does not hold is held to the door's bound on hours as a post's shape is (PROTOCOL.md, What the door answers). So is a line whose wrapper carries a time that is not one as a door writes it, `toISOString` of a date that is one, since the earliest of a wrapper's times decides an event's order and a lease's start (CORE.md section 6), and the reference compares them as text.
- Every other event goes through this door's own admission, the same code a `POST` goes through: the core's checks (the problem is held here, the piece exists, a reveal's return fits the schema and passes the gate, a reveal follows an unrevealed commit) and the layers' (a stake lock on a staked piece, QX-15; a gold rule, QX-16; a human piece's seat, QX-3, read from the peer's wrapper; a record's readings being in, QX-20; a trace naming reads held here, QX-19), and the stamp this door asks of a name (CORE.md section 11), which the event carries, so a name the peer took without it is refused here as a post of it would be. What the door refuses is said in the pull's report with the reason, not folded, exactly as a post would have been refused. The rate limits are not applied: they are the door's cost for a stranger's posts, and a peer's chain is already paid for.
- An event admitted is appended to this tracker's chain as a new line, with the peer's wrappers kept and this door's own added (`by` this tracker, `at` now, and the door's word where it has one, as the coin's lock word is), so the receipt says where the event has been. The earliest wrapper decides the event's time in every fold (CORE.md section 5). Its receipt time is not stamped strictly increasing, as a post's is: a pulled line takes no place in this tracker's own order of receipt, since the tracker did not receive it from the signer.

The coin log (QX-17) is not pulled. A balance is a function of an ordered log, and peers cannot order a log without a consensus the protocol does not have and should not grow; the coin's home keeps the one sequence and borrows its order from the chain it anchors to.

## 3. What converges and what does not

Two trackers that name each other converge on every event both doors admit, which is every event the core accepts and every event their layers' rules agree on, within one pull of each other. They differ where their rules differ: a founding standing one declares and the other does not (QX-1 section 2 as amended), a coin one carries and the other does not (QX-17), a maintainer's hide one honours (QX-6), a stamp one asks of a name and the other does not (CORE.md section 11), a stake rule in force at one door when an event arrived and not yet at the other. Each such difference is one line in the pull's report, with the reason, and is the same difference a client would have met posting to both. A client that reads both computes the same core map from either, since the core's states are a function of the events, and may read different layers' words, which is what the layers are.

A pulled event is folded at the time its earliest wrapper says, which may be before events this tracker received itself; the fold orders by that time, as it always has (CORE.md section 5), so a late pull changes nothing in the order and only adds facts. A window judged open at this door against its own clock may be closed at the peer's; that is the same skew the protocol has always tolerated (PROTOCOL.md, Time).

## 4. What this does not do

- It does not make a tracker hold a problem it was not given.
- It does not take a peer's word for anything: not its layer's states, not its holds, not its hides.
- It does not pull the coin log, and does not replace the mirror, which keeps a chain of its own that only grows for each problem and the identity log, and copies the coin log whole, refusing one that did not only grow ([NODE.md](../NODE.md) section 5); a tracker's own chain still only grows, since a pull appends.
- It does not yet pull from a node (`node: true`); a node's chains reach a tracker through the mirror, or through a client posting what it holds.

## 5. The reference tracker

`Tracker.pullPeers()` runs one pull through the tracker's own door, which it hands `peers.ts` as a `PullDoor`, and returns, per peer, the lines added, the events refused with why, and what could not be read; `schedulePeerPulls` runs it on the clock for both binaries, and the log carries one line per peer per pull. `GET /.well-known/quilt` says `peers` and `pull: { extension: "QX-21", every_ms }`.

## 6. Tests

`packages/tracker/test/peers.test.ts`: two trackers holding one problem, the second naming the first as its peer; readings on the first pulled to the second and its states the same, the lines carrying both doors' wrappers and the chain verifying; a second pull adding nothing; a name on the first's identity log pulled; a hide the first admits from a maintainer it alone names refused at the second's door with the reason a direct post gets, the readings beside it folded, and refused again on the next pull, since a refusal is not remembered; a human piece's reveal pulled where the peer's wrapper says `seat: "person"` or `custody: "hosted"`, and refused where it says neither; a name the peer took without the stamp the second asks refused at the pull with the reason a direct post gets, and a stamped one pulled; a peer that does not answer noted and the rest pulled; and a pull through a `PullDoor` made by hand, the door's admission deciding each event, a refusal said with its reason, a failure noted, and a line admitted carrying the peer's wrapper with the door's after it. `packages/tracker/test/hours.test.ts` holds a peer's claim whose lease is over the door's bound, and a line whose wrapper carries a time not written as a door writes one, refused at the pull with the reason, the door answering throughout.

## 7. The keeper, the same without a door

The mirror ([NODE.md](../NODE.md) section 5) takes a chain as section 2 does, with no door of its own: it reads a source's chain whole, verifies it, and appends every event it lacks, by id, whose shape and signature hold, to a chain of its own, with the source's wrappers kept and its own added. It follows each configured source's peers one hop, and leaves the coin log whole. Three things differ from a door's pull. The mirror takes every problem its sources list, where a door pulls only the problems it holds. It takes each problem in a run from the first source that gives it, where a door pulls every peer's chain for every problem it holds; the identity log it takes from every source that lists its problems. And it refuses only what does not check, where a door refuses what its layer refuses, since the mirror keeps facts and judges none of them. Stage two of one peer, 2 November 2026.
