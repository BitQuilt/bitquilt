# QX-18: the product as witness

Status: Draft. Written and first implemented 1 November 2026 in the hosted on-ramp, the reference tracker's door, state and address reading, and the Quilt client; [AGENTS.md](../../AGENTS.md#the-shape-of-it) names the files that carry it out. [EXTENSIONS.md](../EXTENSIONS.md) says what an extension may do; [OPEN-PROBLEM.md](../OPEN-PROBLEM.md), the note of 1 November 2026, "The product as witness", is where it comes from.

**Abstract.** The vendor on a reveal is the client's own declaration, and nothing checks it. A person in claude.ai or ChatGPT has no API call of their own to prove, since the product makes the calls. What a tracker can see is the door they come in by. A hosted on-ramp that is the OAuth authorization server for its own addresses sees how each token was obtained: the callback the code was sent to, and who redeemed it. The code passes through the person's browser on its way to the product's callback, so the callback alone proves little. This extension has the on-ramp redeem a code sent to a product's callback only in a way that binds the redemption to the product, with the key the product publishes or from the addresses it publishes for its servers, and write the product beside `custody: hosted` on every event it posts for the member: `via: claude.ai` or `via: chatgpt.com`, with `via_by` saying which binding held, or `via: other` with the name the client gave itself. The mark is recorded and shown. Nothing counts it yet.

## 1. The authorization server

The on-ramp follows the MCP authorization spec and OAuth 2.1, with these routes beside the tracker's:

| Route | What it is |
| --- | --- |
| `GET /.well-known/oauth-protected-resource`, and the same with `/mcp` after it | The protected-resource metadata (RFC 9728): the resource `<tracker>mcp`, the issuer, the one scope `quilt`, the bearer in the header. |
| `GET /.well-known/oauth-authorization-server` | The authorization-server metadata (RFC 8414): the endpoints below, `code` alone, PKCE with `S256` alone, client metadata documents supported, signed token requests supported, the issuer named in each authorization response (RFC 9207). |
| `POST /oauth/register` | Dynamic client registration (RFC 7591), for clients without a document of their own. |
| `GET /oauth/authorize` | The authorization page, where a person presents the address they hold, or makes a new one there (the join route, called from the page), so sign-up happens inside the connection. |
| `GET /oauth/authorize/request` | What the page shows of a request: the client, by the host of its document where it has one and by its own name, where the code goes, and the mark that follows. |
| `POST /oauth/authorize` | The person's answer: declined, or an address presented and a code sent. |

The site, bitquilt.org, is a client of this server by its own metadata document (`https://bitquilt.org/.well-known/oauth/client-metadata.json`: `none` at the token endpoint, PKCE in the browser, its login page the callback). A member logs in there and the site reads the window's reader, `/window/io`, with the token, so the directory shows them their own; the grant says `other` with the site's name, since the site witnesses nothing and makes no call in the person's name.
| `POST /oauth/token` | The code for tokens, with the PKCE verifier; a refresh token for the next pair. |
| `POST /oauth/revoke` | Revocation (RFC 7009): a token of the client's ends its grant. |

- **Clients by document.** A client whose id is an https URL is read at that URL (the spec's client ID metadata documents, which claude.ai and ChatGPT both use when a server advertises them). The URL has a path, no fragment and no credentials, and names a public host; the document is fetched with no redirect followed, read to 16 KB and no further, as JSON, through the guard that refuses a private address at the lookup the connection itself makes (`QUILT_READS=public`, as QX-19 section 6 says), and kept as its cache headers say, between a minute and a day, with errors never kept. Its `client_id` is its own URL. It authenticates at the token endpoint as `none` or with `private_key_jwt`, and a client that signs publishes its keys on its own host (`jwks_uri`) or inline. The page names such a client by the host of its URL, which only that host's owner can serve, and shows its `client_name` as its own word.
- **Clients by registration.** One to ten redirect URIs, each https, http on the same machine alone (`localhost`, `127.0.0.1`, `[::1]`), or a native app's own scheme, and none with a fragment. The client authenticates by `none`, `client_secret_post` or `client_secret_basic`; a secret is handed out once and kept as its hash. A registration cannot carry a key: a client that signs its requests identifies itself by a document. The client's name is kept when it passes the plain-text gate and is at most 80 characters; otherwise the client is registered without one.
- **Authorization.** `response_type=code` with a PKCE challenge by `S256`, and a redirect URI the client's document or registration names, compared whole (on the loopback, any port, as RFC 8252 asks). A request through a product's callback (section 2) names the resource it is for, this connector, as RFC 8707 asks, so a token for this connector is never obtained by a product that thought it was connecting to another server. An unknown client or redirect URI is said to the person; any other fault goes back to the client at its redirect URI. The person proves they hold an address by pasting it: the long address, or its last part. The code is good for five minutes and once; a second use revokes the grant the first gave.
- **Signed token requests.** With `private_key_jwt` (RFC 7523) the request carries a JWT signed with RS256, PS256 or ES256 by a key the client's document publishes, whose issuer and subject are the client id, whose audience is the token endpoint or the issuer, with an expiry within a day, and with a `jti` this server keeps and takes once.
- **Tokens.** Signed with the key in `QUILT_OAUTH_SECRET` and naming their grant. An access token lasts an hour; a refresh token ninety days, and each refresh hands out the next pair. An older refresh token presented again is someone else's copy, and the grant ends. A grant is a row in the tracker's store, one per authorization, holding the member, the client, the redirect URI the code was sent to and the mark (section 3); a revoked grant's tokens stop working.
- **The connector.** `/mcp` takes a bearer token and nothing else, and answers a request without one with 401 and the challenge naming the metadata. The long address, `/mcp/<token>`, works bare as before, and a header this server did not issue changes nothing there; a token it did issue, beside the long address, brings its witness when it is for that same address, and is refused when it is for another.
- **What a token lets a client do.** The connector's tools, as the address gives them. It does not open `/key` or `/sheet`.

## 2. The products

| Product | Callbacks | Its own origins | Published addresses |
| --- | --- | --- | --- |
| `claude.ai` | `https://claude.ai/api/mcp/auth_callback`; `https://claude.com/api/mcp/auth_callback`, which Anthropic says it may move to | `https://claude.ai`, `https://claude.com` | `160.79.104.0/21`, the outbound range Anthropic's IP page gives for MCP tool calls, "stable" and not to change without notice |
| `chatgpt.com` | `https://chatgpt.com/connector_platform_oauth_redirect`; `https://chatgpt.com/connector/oauth/<id>`, the id one to 128 letters, digits, `_` and `-` | `https://chatgpt.com` | none written here: OpenAI's egress ranges are a feed of hundreds of prefixes that changes often, and ChatGPT binds by its key instead |

A callback is compared as a whole string: scheme, host, path, and no port, user, query or fragment. Read 1 November 2026 from Anthropic's connector documentation and IP page, and from OpenAI's connector documentation, which also says that ChatGPT's document is at `https://chatgpt.com/oauth/client.json`, that it prefers `private_key_jwt` with RS256 and publishes its keys at `/oauth/jwks.json`, and that ChatGPT signs its token requests server-side. Anthropic's hosted apps identify themselves with a document Anthropic hosts and authenticate as a public client, so claude.ai binds by address. `QUILT_WITNESS_RANGES` replaces the published addresses, per product. A product is added by a line in `products.ts` and a test.

## 3. The binding and the mark

At the token exchange, the code's redirect URI names a product or it does not.

- **Through a product's callback**, the request is bound **by key** when it authenticated with `private_key_jwt` against a document on one of the product's own origins; or **by address** when it came from the product's published addresses, the client's address being read past the trusted proxies as section 7 says. Both holding, the key is recorded. Neither holding, the code is refused with `invalid_grant` and one sentence naming what would have bound it: a code sent to the product's callback is redeemed by the product. A grant so made refreshes only under the same binding.
- **Through any other callback**, the request is redeemed as the client it was given to, with no binding asked, and the grant says `other` with the client's own name.

On every event the hosted on-ramp posts through a session opened with a token, the receipt's wrapper carries the mark beside `custody` and `seat`:

```json
{ "by": "https://tracker.bitquilt.org/", "at": "…", "custody": "hosted", "seat": "ai", "via": "claude.ai", "via_by": "address" }
{ "by": "https://tracker.bitquilt.org/", "at": "…", "custody": "hosted", "seat": "ai", "via": "chatgpt.com", "via_by": "key" }
{ "by": "https://tracker.bitquilt.org/", "at": "…", "custody": "hosted", "seat": "ai", "via": "other", "via_client": "Acme Agent" }
```

- `via` is the product the grant was bound to, else `other`. The client's name, its other metadata and the name it gives in the MCP handshake decide nothing.
- `via_by` comes with a product alone: `key` or `address`.
- `via_client` comes with `other` alone: the name the client registered or published, through the gate, at most 80 characters. It is the client's own word, and is shown only quoted.
- The door writes the mark only on a post that carries the custody secret (`x-quilt-custody`), from `x-quilt-via`, `x-quilt-via-by` and `x-quilt-via-client`, the name encoded. From anyone else those headers are not read. The on-ramp sends the secret and those headers to its own door alone: a member's post to any other tracker, one a link named included, carries neither. A `via` that is not a host name in lower case or `other`, a `via_by` that is not one of the two, or a name that fails the gate, is left out.
- A session opened at the bare address carries no mark, and neither does any event a key of its own posts.
- The wrapper is the resolver's word (CORE.md section 5): a core client ignores the fields, the chain covers them (QX-11), and the mirror copies them.
- `/p/<hash>/state` lists on each piece `witnessed`: one `{ key, via, via_by?, via_client? }` for each reveal on the problem's chain whose receipt names a witness, in chain order.
- `/.well-known/quilt` carries `witness`: the extension, the connector's address, and for each product its callbacks and `bound_by`, the bindings this tracker accepts for it (`key` always; `address` where it has the product's ranges).

## 4. What it says, and what it does not

It says that the token behind the event was obtained through the product's callback and redeemed by the product: with a key the product publishes where only it can publish, or from servers only the product runs. A product runs one vendor's models, so a mark of `claude.ai` puts the calls inside Anthropic's product and a mark of `chatgpt.com` inside OpenAI's. The code's passage through the person's browser no longer matters: holding it buys nothing without the product's key or the product's servers.

It does not say:

- **Who wrote the answer.** A person can type a return and have the product hand it back. The mark attests the product that made the calls, not the person's own typing.
- **Anything of the local connectors.** Claude Desktop and Claude Code over stdio, and a Quilt at home, hold no token from this server, and any process can give itself any name in the handshake. They carry no mark.
- **More than the tracker's word, which rests on three others.** The product's: its document, its keys and its address ranges are what it publishes, read on a day and kept as its cache headers say, and a range that moves without notice ends that product's connections here with a plain reason until `QUILT_WITNESS_RANGES` is updated, while the long address goes on working. The proxy's: the address the tracker reads is what its trusted proxy wrote, so a deployment that trusts a proxy it should not, or sets Caddy to pass a client's own forwarding header through, weakens the address binding to that proxy's word (section 7). The clock's, for an assertion's expiry.
- **That the product's key or servers were not misused.** A key binding is as good as the product's custody of its key; an address binding is as good as the product's control of what its servers send. A person who could make the product's own backend redeem a code of their choosing for this connector would be witnessed. The one such path known, a server of the person's own that points the product at this tracker as its authorization server, is closed by the resource rule: the product names the server it is connecting to, and this server issues tokens for its own connector alone.
- **That a product cannot weaken its own binding.** ChatGPT's document allows `none` beside its key; this server refuses a code sent to ChatGPT's callback redeemed as a public client, so ChatGPT itself has to sign, which its document says it prefers and its published behaviour does. Were it to stop, its connections here would stop with a plain reason rather than carry a weaker mark, and the tracker's keeper would add OpenAI's published ranges to `QUILT_WITNESS_RANGES`.

## 5. The client

- `quilt_read` names the witness beside each accepted return's signer, "(witnessed by claude.ai)" or "(through a client that calls itself "Acme Agent")", and says in one line under the list what a witness is. It reads the mark from the receipts' wrappers, the first that names one, and leaves out a mark of another shape, a binding of another shape, and a name that fails the gate.
- `quilt_me`, in a hosted session opened with a token, says "Witnessed by claude.ai", with how the token request was bound and what that means, or "Witness: none" with the client's own name quoted. Its handles carry `witness` as the `via` alone, so the client's name reaches a model only in the text, quoted.

## 6. What may read it later

The independence rule is unchanged: a square still turns on two reveals from different declared vendors (CORE.md section 6). The open problem's note names three grades of a vendor, proven, witnessed and declared, and this mark is the middle one's evidence. A later extension may compute the grade of the pair that accepted a square from it, distinguish a key binding from an address binding, let a pattern set a floor, or weight standing by it, without changing the reducer. Such a rule reads the mark as section 4 says it is: the tracker's word that the product redeemed the token, resting on what the product publishes and on the tracker's own proxy.

## 7. Configuration

- `QUILT_OAUTH_SECRET` is the key tokens are signed with, from the environment and never from code; unset, the on-ramp has no authorization server and an address is its own credential, as before.
- `QUILT_OAUTH_ISSUER` is the issuer the metadata names, the tracker's address without its trailing slash unless set.
- `QUILT_WITNESS_RANGES` is one JSON object of product to address ranges, replacing the published ranges in `products.ts` for the products it names; a product with an empty list binds by key alone.
- `QUILT_TRUSTED_PROXIES` names the proxies whose `X-Forwarded-For` the tracker and the on-ramp believe, as ranges: the machine itself and the private networks unless set, `none` to believe no header. The header is read only when the connection's peer is a trusted proxy, and then from the right, past every trusted hop, to the first address that is not one. Caddy, as `deploy/Caddyfile` runs it, ignores a client's own forwarding header and writes the client's address itself, so the compose network's default is right; a proxy in front of Caddy is named in both Caddy's `trusted_proxies` and this list.

[DEPLOY.md](../DEPLOY.md) says how the public tracker sets them.
