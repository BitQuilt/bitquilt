# QX-18: the product as witness

Status: Draft. Written and first implemented 1 November 2026 in the hosted on-ramp (`packages/hosted/src/oauth.ts`, `products.ts`), the reference tracker's door and state, and the Quilt client. [EXTENSIONS.md](../EXTENSIONS.md) says what an extension may do; [OPEN-PROBLEM.md](../OPEN-PROBLEM.md), the note of 1 November 2026, "The product as witness", is where it comes from.

**Abstract.** The vendor on a reveal is the client's own declaration, and nothing checks it. A person in claude.ai or ChatGPT has no API call of their own to prove, since the product makes the calls. What a tracker can see is the door they come in by. A hosted on-ramp that is the OAuth authorization server for its own addresses knows which callback each token's code was sent to, and a product's callback is received by that product's backend, which exchanges the code. This extension has the on-ramp write that product beside `custody: hosted` on every event it posts for the member: `via: claude.ai`, `via: chatgpt.com`, or `via: other` with the name the client gave itself. The mark is recorded and shown. Nothing counts it yet.

## 1. The authorization server

The on-ramp follows the MCP authorization spec and OAuth 2.1, with these routes beside the tracker's:

| Route | What it is |
| --- | --- |
| `GET /.well-known/oauth-protected-resource`, and the same with `/mcp` after it | The protected-resource metadata (RFC 9728): the resource `<tracker>mcp`, the issuer, the one scope `quilt`, the bearer in the header. |
| `GET /.well-known/oauth-authorization-server` | The authorization-server metadata (RFC 8414): the endpoints below, `code` alone, PKCE with `S256` alone, the issuer named in each authorization response (RFC 9207). |
| `POST /oauth/register` | Dynamic client registration (RFC 7591). |
| `GET /oauth/authorize` | The authorization page. |
| `GET /oauth/authorize/request` | What the page shows of a request: the client's own name, where the code goes, and the mark that follows. |
| `POST /oauth/authorize` | The person's answer: declined, or an address presented and a code sent. |
| `POST /oauth/token` | The code for tokens, with the PKCE verifier; a refresh token for the next pair. |
| `POST /oauth/revoke` | Revocation (RFC 7009): a token of the client's ends its grant. |

- **Registration.** One to ten redirect URIs, each https, http on the same machine alone (`localhost`, `127.0.0.1`, `[::1]`), or a native app's own scheme, and none with a fragment. The client authenticates at the token endpoint by `none`, `client_secret_post` or `client_secret_basic`; a secret is handed out once and kept as its hash. The client's name is kept when it passes the plain-text gate and is at most 80 characters; otherwise the client is registered without one.
- **Authorization.** `response_type=code` with a PKCE challenge by `S256`, and a redirect URI the client registered, compared whole (on the loopback, any port, as RFC 8252 asks). An unknown client or redirect URI is said to the person; any other fault goes back to the client at its redirect URI. The person proves they hold an address by pasting it: the long address, or its last part. The code is good for five minutes and once; a second use revokes the grant the first gave.
- **Tokens.** Signed with the key in `QUILT_OAUTH_SECRET` and naming their grant. An access token lasts an hour; a refresh token ninety days, and each refresh hands out the next pair, after which the old refresh token is refused. A grant is a row in the tracker's store, one per authorization, holding the member, the client, the redirect URI the code was sent to and the mark (section 3); a revoked grant's tokens stop working.
- **The connector.** `/mcp` takes a bearer token and nothing else, and answers a request without one with 401 and the challenge naming the metadata. The long address, `/mcp/<token>`, works bare as before, and a header this server did not issue changes nothing there; a token it did issue, beside the long address, brings its witness when it is for that same address, and is refused when it is for another.
- **What a token lets a client do.** The connector's tools, as the address gives them. It does not open `/key` or `/sheet`.

## 2. The callbacks

| Product | Redirect URI |
| --- | --- |
| `claude.ai` | `https://claude.ai/api/mcp/auth_callback` |
| `claude.ai` | `https://claude.com/api/mcp/auth_callback`, the same product's, which Anthropic says it may move to |
| `chatgpt.com` | `https://chatgpt.com/connector_platform_oauth_redirect` |
| `chatgpt.com` | `https://chatgpt.com/connector/oauth/<id>`, the id one to 128 letters, digits, `_` and `-` |

Each is compared as a whole string: scheme, host, path, and no port, user, query or fragment. Read 1 November 2026 from Anthropic's help article on custom connectors and from OpenAI's answers on connector callbacks. A product is added by a line in `products.ts` and a test.

## 3. The mark

On every event the hosted on-ramp posts through a session opened with a token, the receipt's wrapper carries `via` beside `custody` and `seat`:

```json
{ "by": "https://tracker.bitquilt.org/", "at": "…", "custody": "hosted", "seat": "ai", "via": "claude.ai" }
{ "by": "https://tracker.bitquilt.org/", "at": "…", "custody": "hosted", "seat": "ai", "via": "other", "via_client": "Acme Agent" }
```

- `via` is the product whose callback the grant's code was sent to (section 2), else `other`. It is decided at the exchange, from the code's redirect URI alone. The client's name, its other metadata and the name it gives in the MCP handshake decide nothing.
- `via_client` comes with `other` alone: the name the client registered, through the gate, at most 80 characters. It is the client's own word, and is shown only quoted.
- The door writes the mark only on a post that carries the custody secret (`x-quilt-custody`), from `x-quilt-via` and `x-quilt-via-client`, the name encoded. From anyone else those headers are not read. A `via` that is not a host name in lower case or `other` is left out, and so is a name that fails the gate.
- A session opened at the bare address carries no mark, and neither does any event a key of its own posts.
- The wrapper is the resolver's word (CORE.md section 5): a core client ignores the field, the chain covers it (QX-11), and the mirror copies it.
- `/p/<hash>/state` lists on each piece `witnessed`: one `{ key, via, via_client? }` for each reveal on the problem's chain whose receipt names a witness, in chain order.

## 4. What it says, and what it does not

It says that the token behind the event was obtained through the product's callback: the product's backend received the code, exchanged it, and made the calls with the token. A product runs one vendor's models, so a mark of `claude.ai` puts the calls inside Anthropic's product and a mark of `chatgpt.com` inside OpenAI's.

It does not say:

- **Who wrote the answer.** A person can type a return and have the product hand it back. The mark attests the product that made the calls, not the person's own typing.
- **Anything of the local connectors.** Claude Desktop and Claude Code over stdio, and a Quilt at home, hold no token from this server, and any process can give itself any name in the handshake. They carry no mark.
- **More than the tracker's word.** It is written by the tracker that holds the key, as `custody` and `seat` are. Another tracker is not bound by it, and a reader trusts it as far as they trust that tracker.
- **That the product exchanged the code, where the person did instead.** The authorization page sends the person's browser to the product's callback with the code in the address. A person who stops there, takes the code, and exchanges it themself, with a client they registered under the product's callback and a PKCE pair of their own, holds a token marked as that product without the product taking part. The mark is therefore exact about where the code was sent, and binds the product only as far as only the product can exchange a code sent there. Closing that needs something the product alone holds: its registration bound to a key it publishes (a client ID metadata document on its own domain, with `private_key_jwt` at the token endpoint), or the token request held to the address ranges the product publishes for its servers, behind a proxy that passes no forged forwarded address. Neither is built here, and the products do not offer the first today.

## 5. The client

- `quilt_read` names the witness beside each accepted return's signer, "(witnessed by claude.ai)" or "(through a client that calls itself "Acme Agent")", and says in one line under the list what a witness is. It reads the mark from the receipts' wrappers, the first that names one, and leaves out a mark of another shape and a name that fails the gate.
- `quilt_me`, in a hosted session opened with a token, says "Witnessed by claude.ai", with what that means, or "Witness: none" with the client's own name quoted. Its handles carry `witness` as the `via` alone, so the client's name reaches a model only in the text, quoted.

## 6. What may read it later

The independence rule is unchanged: a square still turns on two reveals from different declared vendors (CORE.md section 6). The open problem's note names three grades of a vendor, proven, witnessed and declared, and this mark is the middle one's evidence. A later extension may compute the grade of the pair that accepted a square from it, let a pattern set a floor, or weight standing by it, without changing the reducer. Such a rule reads the mark as section 4 says it is: the tracker's word on where a code was sent, short of proof while the code passes through the person's browser.

## 7. Configuration

`QUILT_OAUTH_SECRET` is the key tokens are signed with, from the environment and never from code; unset, the on-ramp has no authorization server and an address is its own credential, as before. `QUILT_OAUTH_ISSUER` is the issuer the metadata names, the tracker's address without its trailing slash unless set. [DEPLOY.md](../DEPLOY.md) says how the public tracker sets them.
